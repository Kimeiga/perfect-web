01 / THE PROBLEM

The most important rules are missing from the program.

02 / THE SYSTEM

One semantic application. Three execution environments.

The permanent product is not a UI library plus a separate meta-framework. It is a whole-application compiler whose source model includes effects, capabilities, privacy, consistency, resources, and document structure.

04 / PROOF, NOT PROMISES

Every major claim gets a public failure test.

The project should become believable through a ladder of demonstrations. Each proof has a comparator, a failure condition, a measurable output, and an explicit statement of what it does not establish.

Proof 00 · compiler semantics

The Bug Museum

A live gallery of accepted and rejected programs: network in render, private data in a public cache, a browser importing a database, an escaped task, an unclosed transaction, a non-serializable handler capture, and an unhandled business state.

What the visitor sees

They edit a safe program into a dangerous one and receive a domain-specific explanation with safe architectural alternatives.

What it proves

The project has a coherent static model whose errors are useful to an application developer.

Comparator

The equivalent TypeScript or framework pattern that compiles and relies on documentation, linting, review, or runtime tests.

Success condition

Every negative example fails for its intended reason; every accepted example remains stable under incremental edits.

05 / THE FLAGSHIP

A marketplace is the smallest demo that is not a toy.

One domain can force the platform to compose public content, private state, role permissions, transactions, realtime streams, offline work, edge caching, and operational recovery.

The Marketplace

Four applications. One domain model.

A polished open-data marketplace—not proprietary employer code—becomes the end-to-end benchmark. Every route has an inspectable effect, privacy, placement, cache, and document-parts graph.

ROLE / 01

Consumer

Public discovery, private cart, address, promotions, optimistic commands, checkout, and order tracking.

ROLE / 02

Merchant

Catalog edits, item availability, pricing, incoming orders, capability-limited operations, and invalidation events.

ROLE / 03

Courier

Offers, navigation, offline transitions, reconnect policy, location privacy, and authoritative state validation.

ROLE / 04

Operations

Live system state, permissions, audit trace, intervention commands, and degraded-service visibility.

06 / BUILD ORDER

Deployable framework first. New browser second.

The project becomes useful before it changes the web platform. Current browsers are the compatibility target; browser-native work begins only after profiling reveals what the shim actually costs.

Phase 1

Semantic core

Accepted/rejected corpus, algebraic types, effects, capabilities, diagnostics, and the browser compiler playground.

Phase 2

Browser-compatible vertical slice

Semantic HTML, document parts, resumption, queries, commands, streaming, and the first store/cart route.

Phase 3

Distributed marketplace

Edge/origin placement, privacy, capability runtime, materialized views, network lab, and four-role application.

Phase 4

AI and adoption proof

Agent benchmark, semantic PRs, interop, one-feature migration, and the first real pilot outside the demo.

Phase 5

Native web experiments

Servo embedding, direct document-part interfaces, native resumption, declarative patches, and standards proposals.

07 / HONEST BOUNDARIES

A compiler can remove mechanism errors. It cannot invent the product.

The project becomes more credible by stating what remains difficult.

NOT SOLVED / 01

Ambiguous requirements

The compiler cannot know whether a discount, cancellation, substitution, or permission rule is what the business intended.

NOT SOLVED / 02

Physical latency

It can remove waterfalls and place work intelligently, but it cannot abolish distance, slow databases, or external services.

NOT SOLVED / 03

Universal consistency

Offline and distributed conflicts need explicit domain policy. There is no one correct merge strategy.

NOT SOLVED / 04

All outages

Removing a trigger class does not replace capacity planning, isolation, observability, rollback, and fault tolerance.

NOT SOLVED / 05

Foreign ecosystems

JavaScript, native libraries, databases, and third-party APIs weaken guarantees unless their boundaries are decoded and capability-wrapped.

NOT SOLVED / 06

Free compiler complexity

Effects, privacy, placement, and invalidation interact. Diagnostics and incremental compilation are core research work, not polish.
