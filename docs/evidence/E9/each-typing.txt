typed `{#each}` captures — an E9 slice, pulled forward for E7

  `{#each xs as x}` gives `x` the element type of what `xs` holds. E7
  cannot emit a resumable handler inside a loop without it: the capture
  schema is hashed into the resume manifest and compared against the
  schema the running build produced, so a guessed type yields a hash
  that matches nothing.

=== POSITIVE CONTROL — the rule accepts what it should ===================

$ pw check <platform> examples/domain.pw examples/rules/resume/loop-capture-typed.pw
pw check: 31 file(s), no diagnostics

   = note: A resume manifest carries a schema hash derived from what a handler captures, and the running code compares it against the schema its own build produced. A capture whose type this build cannot determine yields a hash derived from a guess, which matches nothing — so every resume of `Broken` would fail after deployment, for a reason nobody could diagnose from the deployment. Name the type here, where it is still a compile error.

  One error, not one error plus unexplained neighbours. The refusal is
  the behaviour under test: a quiet fall back to an ordinary handler
  would make which handlers resume depend on where inference is blind.
