HOW IT IS COVERAGE-GUIDED
  -C instrument-coverage (stable) + llvm-profdata (a component of the pinned
  rustc 1.97.1, so no version in tools/versions.lock changes). Each input runs
  under an instrumented harness; the covered-region set is compared against
  what the corpus has already reached; an input that grows it is kept and
  mutated. That is coverage feedback with an evolving corpus.

WHAT IT IS NOT
  Not libFuzzer. A process per input rather than an in-process loop, so
  executions per second are low and a campaign is thousands of inputs rather
  than millions. `cargo-fuzz` needs nightly and a new dependency; the project
  pins both.

  Not a replacement for the structured generators. Those encode what a CORRECT
  answer looks like; this finds inputs neither the author nor the architect
  thought of. The two are reported separately on purpose — merging them into
  one "fuzzed" badge would hide that the structured suites are the ones
  carrying properties.

A NOTE ON THE FIRST RUN
  It reported ~69 covered regions for the whole compiler. That is implausible
  for a parser plus fourteen analyses, and the implausibility is what exposed
  the bug: the profile parser looked for `Function name: `, which
  llvm-profdata does not emit. It matched nothing in the dependencies. The
  real figure is 1,200-2,300 regions per target.

  Recorded because it is the same failure this project keeps having: a
  measurement that returns a plausible-looking number while measuring almost
  nothing. RISK_QUEUE.md counts it.
