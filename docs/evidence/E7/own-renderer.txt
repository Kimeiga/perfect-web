  HelloStatic, Tricky: 0 script tags, 0 runtime, usable with JS off

THE STORE PAGE — E7-R's vertical slice
  server renderer → HTML with only the required anchors
  → parts manifest → decide() → Authorised → handler attaches
  → click Add → command → only cart-related PartIds update

  40 assertions, 3 engine families:
    no Marko participates in this route
    only dynamic regions carry identity markup
    the page is readable with JavaScript disabled
    a compatible manifest authorises; the handler attaches
    an INCOMPATIBLE manifest is refused and nothing attaches
    the menu keeps node identity across the update
    the cart element survives its content changing, twice
    focus survives the update
    only the cart part id updates
    replacing a menu node makes the identity assertion RED
    handler bytes are still eager — the E7-L gap, recorded

LIVE PART IDENTITY
  IdentityDomain + InstancePath + LocalPartId.
  E6 decides who shares a domain; E7-R decides how things inside it
  are addressed. There is no independent E7 notion of who shares.

  InstanceToken = keyed BLAKE3(identity_key,
                    domain | parent path | each part | key)[0..96 bits]
                  base64url, 16 characters
  and a collision within a domain REFUSES the render — correctness
  does not rest on probability.
  A template part DEFINITION is not a document part INSTANCE: three Add
  buttons share data-pw=0 and have three distinct addresses.
    each loop instance has a distinct address
    every Add button works, not only the last one
    the instance token does not reveal the item key
    the same document renders the same tokens twice

NO COMPONENT REPLAY — structurally, then observed
  the client artifact contains no template renderer, and a poisoned
    artifact makes that check go red
  the client never fetches the server renderer
  a MutationObserver over the whole document sees mutations ONLY inside
    the cart part, and a menu mutation makes that check go red

THE REAL RESOURCE PATH — E6 and E7 composed
  the command returns { committed: true } and no cart value
  the browser learns the value from the RESOURCE, at a version
    rolled-back command      → no browser update
    CartChanged(session A)   → session B unchanged
    duplicate event          → no second transition
    unrelated MenuChanged    → cart unchanged
    stale version arriving   → does not overwrite newer state
                               (and a newer one IS applied)
