Raw output: [bench.txt](bench.txt), produced by `just e10-bench`. E7's

Host: Apple M2 Pro, arm64, macOS; Chromium 145.0.7632.6 (Playwright 1.58.0);

Read with care:

- **The components are not the same programs as the guests.** The guest looks
  up a store and formats a string. Each Pleris command reads the session and
  makes one data-layer call. Both are one call through an imported interface
  wrapped by `wit-component`, which is why the comparison is indicative and
  not like for like. The Pleris artifacts are 20% (`no_std`) to 90% (`std`)
  smaller, and most of every one is component-model wrapping: the core module
  of `add_to_cart` is 423 bytes.
- **The compiled handler modules are larger than the modules the server used
  to write**, by 26 and 66 bytes. The difference is a header comment and an
  `export const handler` line that names the module's identity. They are sent
  once, on first interaction, per handler.
- **The runtime grew 1,511 bytes**: the `command` function, captures, and the
  reload recovery. It ships unminified, comments included, as it did at E7.

## Performance: the host, in release

Seven rounds of 2,000 calls after a warm-up round. Each call is what the
development server does per request: a linker from the call's `Granted`, a
fresh store and instance, the call, the drop.

| | compile once | per call, median | min–max |
|---|---:|---:|---:|
| Pleris `add_to_cart` | 0.9 ms | 21.1 µs | 20.2–23.2 µs |
| hand-written Rust `no_std` guest | 2.4 ms | 22.1 µs | 21.4–24.8 µs |
| the data layer's `add`, called natively | — | 0.30 µs | 0.295–0.299 µs |

The compiled command costs the same as hand-written Rust through the same host.
Both pay about 21 µs of per-call instantiation, roughly seventy times the
operation they perform. That is the host's cost, not the compiler's.
Instantiating once per grant (Wasmtime's `InstancePre`) is where the next
reduction would come from, and it is not claimed here.

## Performance: the browser

**Activation**, the runtime's own `pw:activate` measure. Chromium, one
worker, the runtime before compiled handlers (`83af93c`) against the current
one, **interleaved**: before, now, before, now, over seven rounds of three
samples each (`spikes/own-renderer/activation-compare.sh`). Three runs, the
last of them the one recorded in [bench.txt](bench.txt) at `6545029`:

```text
before   median 15.80 ms   interquartile 15.40-16.70   n=21
now      median 15.70 ms   interquartile 15.20-16.40   n=21

before   median 15.80 ms   interquartile 15.10-16.70   n=21
now      median 15.70 ms   interquartile 15.00-16.40   n=21

before   median 16.30 ms   interquartile 15.50-17.70   n=21   (recorded)
now      median 15.50 ms   interquartile 10.50-16.90   n=21   (recorded)
```

The samples cluster around 4-5, 10-11 and 15-18 ms on both sides. Whatever
chooses the cluster is in the machine, not the runtime.

No measurable change, which is what the code predicts: the activation path
lost one unused variable.

**Two corrections made while recording, both kept here.**

1. The recipe's first version compared one activation sample with E7's
   recorded 22.70 ms and printed 4.20 ms. A fivefold "improvement" would have
   gone into this file. It was a low first sample (each run above has some
   near 4 ms), taken on a newer Chromium than E7's 2026-08-07 record. The next
   single sample was 18.70 ms.
2. The second version measured in blocks: eleven of one runtime, then eleven
   of the other. Three runs gave medians of 15.9/16.4, 15.7/15.5 and, at
   `e7d5f19`, **10.3/15.7**. The last looked like a regression of half again.
   Its "before" samples were bimodal (9.2–11.8 and 14.5–16.5): the machine's
   state drifted between the two blocks by more than anything E10 changed.
   Interleaving shares that drift between the two sides, and the two
   interleaved runs agree with each other.

**E7's other measurements, re-run:** interaction long frames 0 (worst 0 ms),
runtime layout reads 0, and the decision wasm unchanged at 74,222 bytes.

## Not claimed

- **Comparisons with other frameworks.** Next/React, SvelteKit and Marko
  baselines are charter §18.1's, at Milestone 3, and none is established.
- **Allocation and throughput under concurrency.** One thread, one component
  at a time.
- **The per-call instantiation cost is not reduced.** It is measured and named.
