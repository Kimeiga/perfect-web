# E10: resumable handlers, compiled to JavaScript modules, 2026-09-25

Raw output: [handlers.txt](handlers.txt), produced by `just e10-handlers`. The
modules are in [handlers/](handlers/), written by `pw emit-handlers` and held to
the compiler's current output by `pw-core`'s `evidence_is_current`. Decision
record: [ADR-0033](../../DECISIONS/ADR-0033-compiled-handlers.md).
Environment: Darwin arm64 (Apple M2 Pro), rust 1.97.1, wasmtime 47.0.4,
Playwright 1.58.0.

## The obligation

E10's gate asks that the store build "from source to browser artifacts … without
Koka or Marko", and charter §14 M10 task 2 lists "generated modern JavaScript
modules for handlers" first. After E10-I the commands were compiled, but the
page's behaviour was not:

- the development server wrote each handler module itself;
- the browser sent the pressed instance's address and the literal quantity;
- the server resolved the address back into an item (ADR-0032 §8).

## What compiles

```text
on:press={resumable(captures = { item }) => add_to_cart(item.id, PositiveInt(1))}
on:press={resumable() => clear_cart()}
```

`pw emit-handlers`, over the same unit set `pw check` accepts:

```js
// e1ab9fca1f6fc15b.mjs
export async function run(context) {
  return await context.command("store.page.add_to_cart", [context.captures["item"]["id"], 1]);
}
// 5e53c6a9aaee307a.mjs
export async function run(context) {
  return await context.command("store.page.clear_cart", []);
}
```

The file names are the resume manifest's identities, the same ones the document
names and `decide` authorises. `PositiveInt(1)` is sent as `1`, the opaque
type's representation. `store.page.add_to_cart` is the contract's own component
id.

What the handler reads, `item.id`, is exactly what the renderer puts on the
element:

```html
<button data-pw="0" type="button" data-pw-captures="{&quot;item&quot;:{&quot;id&quot;:&quot;espresso&quot;}}">
<button data-pw="1" id="clear-cart" type="button">
```

The item's name and every other field stay out of the document, and the Clear
button, whose handler reads nothing, carries nothing.

## The boundary

The module runs in the user's browser, so what reaches the server is a claim.
`POST /command/store.page.add_to_cart` with `["cortado", 2]` is converted by
the parameter types the committed artifact declares, `(string, s64)`, through
Wasmtime's type reflection. These are refused before anything runs, with HTTP
400 and nothing committed. Between them, the host tests, the dev server's tests
and the browser suite send each one:

- one argument, or three;
- `7` where a string is declared;
- `1.5`, `true`, `null` or `"1"` where an integer is declared;
- 2^64 − 1 for an `s64`;
- an object instead of an array.

## Controls

| control | result |
|---|---|
| a handler calling a query (`Look`) or a function (`helper`) | refused: "does not call a command" |
| `Qty(1 + 1)`, `Qty(helper(1))` | refused: computation in the browser |
| `Buy(sku, ..)`, where the page's `sku` is not captured | refused: the document would not carry it |
| `Qty(9007199254740993)` | refused: beyond ±2^53; `9007199254740992` compiles |
| a command taking a record | refused: a parameter a browser cannot send |
| a string with an escape | refused: the language does not define escapes (A-023) |
| the store without its standard packages | nothing compiles: the program does not check |
| the renderer given a missing path, 2^53 + 1, raw HTML | the render is blocked |
| the dev server without compiled modules | refuses to start |
| per-command Rust, `menu_item_at`, a server-written module | a structural test fails if any returns |
| the old `?instance=` route | 404 |

## Found on the way

1. **The component id had three derivations.** Two were inline in
   `contract.rs`, and a third was in `backend/lower.rs`. A `wit.rs` map was also
   keyed by the same format. All four now call `contract::component_id`. They
   agreed; nothing checked that they did.
2. **`clear_cart` committed its event and not its state.** After a clear, the
   materializer's `cart:<session>` held the old total. Nothing read it, so
   nothing failed. With one command path it is `"0"`, and a test holds it.
3. **The Wasm IR's string constants were source tokens.** `Const::Str` held
   `"espresso"` with its quotes. No artifact carried one, because the encoder
   refuses constants that need memory. Now it holds the value, and a string
   whose value would need an escape rule is refused: the language defines
   none (A-023, ruling needed).
4. **`store.spec.mjs`'s identity-markup check matched `data-pw-captures`.** The
   check exists for the ruling "never put raw domain keys into identity markup
   merely for renderer convenience". Carried captures are §8.5's resume
   metadata, so the check now excludes that one attribute by name (A-022,
   ruling needed).
5. **The component's WIT parameters are named `arg0`, `arg1`.** Not a
   correctness issue, but a refusal says "argument 1 (`arg0`)" where
   `item` would be clearer. `wit.rs` names parameters by position.

## Browser suite

Recorded by `just e10-browser "chromium firefox webkit"
docs/evidence/E10/handlers-browser-suite.txt` in
[handlers-browser-suite.txt](handlers-browser-suite.txt), against `f8adc03`:
**Chromium, Firefox and WebKit, 273 of 273, in three consecutive full runs.**
That is the 258 of E10-I, plus the five tests in
`e2e/compiled-handler.spec.mjs` in each engine.

**The first recording failed, and it is kept.** Against `687aaf4`, the commit
that compiles the handlers,
[the first run](handlers-browser-suite-687aaf4.txt) was 273, 272 and 273. The
failure was WebKit's `store.spec.mjs` "only cart-related part ids update". It
was diagnosed rather than retried away:

1. The same test, alone and repeated 25 times: 25 passed. Twelve more full
   three-engine runs: all 273. So the failure needed the rest of the suite
   running beside it.
2. The runtime's `window.__pw.updated` holds what the LAST batch updated. A
   long poll's empty batch cannot reset it on the streaming path, which writes
   only non-empty batches. A probe confirmed it survives a 1.5 s idle.
3. A menu change is broadcast to every page on a host. The harness already
   gives the suites that mutate the menu a host per engine (`keyed-list`,
   `transport`, `performance`), but `public-fragment.spec.mjs` renames an item
   and back and ran on the shared host.
4. Reproduced on demand. A page updated its cart (`updated` = the cart part);
   a second browser context renamed an item; `updated` became the renamed
   item's text part. That is the assertion that failed.

The fix is in the harness (`f8adc03`): `public-fragment` gets its own hosts.
Isolated, its rename then landed inside a sibling test's byte-for-byte
comparison ("Gibraltar" against "Cortado"), so it also runs serially, as the
other isolated suites do. After both changes: six consecutive full runs of
273, then the three recorded above. None of this involves handler code. The
race was in the harness from the day `public-fragment` joined the shared host.

## Not claimed

- **Captures are not a patched part.** A captured field that a patch changes
  without re-rendering its element keeps its rendered value. The store's
  handler reads only the loop's key.
- **Opaque invariants are not checked.** `PositiveInt` arrives as any `s64`.
- **The handler set is narrow.** Parameters (the event), local computation,
  branches and multi-statement bodies are refused by name.
- **The data layer is the deployment's.** `store:data/carts` is `owner:
  external` (NEXT step 10).
