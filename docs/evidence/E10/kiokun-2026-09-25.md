# E10: the kiokun slice — entry lookup and search over one shard, 2026-09-25

Raw output: [kiokun.txt](kiokun.txt), produced by `just e10-kiokun` with
`KIOKUN_DATA` naming a kiokun-data checkout. Decision records:
[ADR-0037](../../DECISIONS/ADR-0037-kiokun-slice.md) for the slice, and
[ADR-0036](../../DECISIONS/ADR-0036-matches-fields-variants.md) for the backend
it needed. The compiler's output is committed as [kiokun/](kiokun/).

## What it is

A piece of kiokun.com, a Chinese–Japanese dictionary, written in Pleris:

```text
examples/kiokun/dictionary.pw   the entry and search-hit types
examples/kiokun/Entries.pw      entries#get   (the deployment's data layer)
examples/kiokun/Index.pw        index#search  (the deployment's data layer)
examples/kiokun/app.pw          Lookup, Search; EntryPage, SearchPage, NotFound
```

`pw build` compiles it to two audited components, `Lookup` (3,164 bytes) and
`Search` (2,411 bytes), and three templates. `spikes/kiokun/server`:

- supplies the data layer over shard `han-1char-3`, read in kiokun's own
  raw-DEFLATE format with kiokun's shard rule;
- runs the components through the E8 host;
- renders the pages.

The pages carry no script.

## Found by building it

1. **The platform package depended on the store example.** `device.pw`
   imported `Location` from `examples/domain.pw`. It is now declared in the
   platform, which checks alone.
2. **The template IR wrote `href="/{hit.target}"` out literally.** A string
   with a hole now blocks the render, naming the supported form.
3. **The checker did not check exhaustiveness over `Option` and `Result`.**
   The backend refused a match with a missing case, and the checker passed it.
   Fixed after this record: the checker now refuses it with PW0305, and both
   of `Lookup`'s matches are proven exhaustive
   (`compiler/pw-core/tests/match_exhaustiveness.rs`,
   [ADR-0038](../../DECISIONS/ADR-0038-every-match-typed.md)).
4. **Search needs one hit per entry**, as kiokun groups them. The first design
   gave two hits for `人`.

## What the slice says about rewriting kiokun.com

What this shows works, end to end, on real data: compiled server logic
(redirects), a real data layer behind capabilities, static server-rendered
pages, search, and three browsers.

What the full site needs that is not built:

- **Pure computation in Pleris.** The standard library's list functions are
  signatures with stub bodies, there are no string functions, and the backend
  compiles no arithmetic or `if`. kiokun's shard rule, its ranking and its
  kana conversion are all in the host.
- **Templates:** an interpolated attribute; an `else`; an `Option`.
- **Every other shard, and the other features:** Korean, character pages,
  names, "contains", pitch accent, learning features, the offline app.
- **A production host.** The slice's server is a spike, like the store's.

## Not claimed

- **Search parity with kiokun.com.** This is kiokun's scoring reimplemented
  over one shard in memory, not FTS5. Japanese has no romaji here, and the
  alias table covers simplified-form stubs only.
- **Load time** is 9.5 s, mostly scanning 186,000 files in the 32 directories
  the shard shares with others. It was not optimised.
