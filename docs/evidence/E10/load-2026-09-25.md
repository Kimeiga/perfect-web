# E10 gate item 3: leaks and unbounded growth under sustained load, 2026-09-25

Raw output: [load.txt](load.txt), produced by `just e10-load`. Decision record:
[ADR-0035](../../DECISIONS/ADR-0035-bounded-subscribers.md).
Environment: Darwin arm64 (Apple M2 Pro), rust 1.97.1, wasmtime 47.0.4.

## The obligation

> Memory leaks and unbounded resource growth are tested under sustained load.
> — charter §14 M10 gate

Two paths carry the store's load: the development server (the protocol's
server side, the materializer, the data layer) and the E8 host running the
compiled commands. Both were measured before anything was changed.

## Measured before the bound

At `41ccaf6`, with the same scenarios as the test that now holds the bound
(it printed and asserted nothing then):

| scenario | frames held | subscribers | outbox rows | materialized entries |
|---|---|---|---|---|
| one session, 3,000 commands, every batch acknowledged | 0 | 1 | **3,000** | — |
| 1,000 visitors load the page and leave; 300 menu changes | **600,000** | 1,000 | — | **1,001** |

Three leaks, none of which a functional test could notice:

1. **The outbox kept every event.** A consumed event was marked `consumed_at`,
   a column nothing ever read. So 3,000 commands left 3,000 rows.
2. **A departed visitor received every change forever.** A frame leaves a queue
   only when its subscriber acknowledges it, and a menu change is pushed to
   every subscriber. A closed tab never acknowledges again: 1,000 visitors and
   300 changes held 600,000 frames, 2 per change per visitor.
3. **A departed visitor's cart fragment stayed materialized.** 1,000 visitors
   left 1,000 entries beside the shared menu.

## After

| scenario | frames held | subscribers | outbox rows | materialized entries |
|---|---|---|---|---|
| one session, 3,000 commands | 0 | 1 | **0** | — |
| 1,000 visitors, 300 menu changes | **1,000** (one reload each) | 1,000 | — | 1,001 |
| the same, 120 s later, at the next change | **0** | **0** | — | **1** (the menu) |

What changed:

1. **`pw-materialize` deletes a consumed event.** `AUTOINCREMENT` keeps a
   deleted id from being reused, so the outbox is still read in commit order.
2. **A subscriber's queue holds at most 256 frames.** One that falls further
   behind gets a single `Recovery::Reload`, the protocol's "this document
   cannot continue", and nothing more until it is re-rendered.
3. **A subscriber that has not asked for 120 s is forgotten**, and so is its
   session's materialized cart entry. `drain` regenerates a missing entry from
   state, so a returning visitor's cart is intact: the test adds to a
   forgotten visitor's cart and serves them a document showing it. Eviction
   runs outside the subscriber table's lock, because `drain` takes the
   materializer and then the table.
4. **A forgotten page that polls is told to reload.** Serving a document now
   takes a sequence number, so a served page's cursor is never zero. A poll
   with a nonzero cursor for a session the server does not hold is therefore
   a page that missed frames, and it gets
   `{"cursor":7,"frames":[{"frame":"recovery",…,"recovery":{"recovery":"reload"}}]}`,
   tested through the real route. Cursor zero is still an ordinary new
   subscriber.
5. **The browser runtime acts on `Reload`.** It had only logged every
   recovery, so a page told to reload would have stayed wrong without saying
   so. It now reloads, once. Other recoveries are still recorded and not acted
   on. `e2e/recovery.spec.mjs` covers all three in each engine.

## The compiled command

`add_to_cart` through `Prepared::call_within`, 1,000 calls to warm up, then
19,000 more. Each call admits, builds a linker from its own `Granted`,
instantiates in a fresh store, runs and drops:

```text
debug    resident 29360 KiB -> 29376 KiB (+16 KiB), 134.1 µs per call
release  resident 12960 KiB -> 12960 KiB (+0 KiB),   24.1 µs per call
```

The bound in the test is 16 MiB over the 19,000 calls. The release figure was
taken with `cargo test --release`; `just e10-load` records the debug run.

## Not claimed

- **Per-session data is not bounded.** A cart is the store's data and is kept.
  What is bounded is what the server holds for a subscriber (its frames, its
  queue, its cached fragment) and what it keeps after use (the outbox).
- **Time is simulated in the idle step.** The test moves each subscriber's
  last-seen time back past the 120 s limit rather than waiting two minutes.
- **The development server is not the production host.** The bounds live in
  its protocol code, the materializer (`pw-materialize`) and the runtime.
  The first and third are what E8's production host must preserve.
