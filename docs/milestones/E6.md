# E6 — Materialized resource graph

**Status: COMPLETE.** All six gate items pass.

## Question

> Can public pages and fragments be incrementally materialized and invalidated
> from **semantic dependencies** rather than route-level timers?

**Answered: yes, and the interesting part is what "semantic" costs.** A
dependency the compiler has never resolved is a string, and a graph of strings
regenerates nothing while looking exactly like a graph that works.

## What ISR gets wrong, stated precisely

A route timer has two settings and both are wrong. Too long serves stale
content; too short recomputes work nobody needed. Neither is an *error* — the
page is well-formed either way — so neither is ever fixed, and the number lives
in a config file where it is tuned by whoever last got paged.

Invalidating from dependencies replaces a number with a claim:

```text
MenuChanged(store_47)  →  store 47's menu fragment, and nothing else
```

That claim is checkable, which is the whole difference. `just materialize`
prints the graph it is derived from and counts both sides of it.

## The graph is compile time; the entries are run time

```text
compile time   MenuFragment(id) --reads--> Menu(id)
               MenuFragment(id) --invalidated-by--> MenuChanged(id)

run time       MenuFragment(47) reads Menu(47)
```

There is no node for "store 47", because a key is a value. The compiler
produces the **schema** — nodes per declaration, edges labelled with the key
expressions connecting them — and the materializer instantiates it per key. A
graph that claimed to know which instances exist would be claiming to know the
contents of the database.

The schema carries enough for the gate because an edge records which parameter
of an event flows into which key position. That is what makes
`MenuChanged(store_47)` narrower than "the menu changed", and an event with no
arguments correspondingly reaches every instance — the honest reading of a fact
that says nothing about which store.

## What implementing it found

**Three defects, all of the same kind: a clause nobody read.**

### 1. A `materialize` block's policies were not policies

Corpus A-009 and R-017 have written their policies inside the declaration's
braces since C0, and the grammar parsed that block as an expression body. So
`depends_on Store(id), Menu(id)` arrived as a bare name followed by two calls,
and `decl.policies` was **empty for every materialization in the corpus**.

An empty dependency list is indistinguishable from "depends on nothing".

Two things had been built on top of it:

- `contexts.rs` classified `depends_on Store(id)` as a region belonging to
  another declaration, so the effect checker would not read it as a call. A
  correct fix to the wrong layer: it worked, and it concealed the parse defect
  underneath. Deleted — a policy never enters the expression arena.
- `reuse_of` read `partition public` by scanning adjacent name expressions.

R-017 went red the moment the parse was fixed and green again when the lowering
learned to look in the second position. It had been passing for a reason
unrelated to the rule it declares.

### 2. Two parsers, four disagreements

`grammar.rs` and `parser.rs` each had their own copy of `DECL_STARTERS`, the
UI/resource noun tables, `POLICY_KEYWORDS`, and their own whitespace handling
for policy values. Adding `event` updated one of each.

The result was a file that was a declaration to one parser and "expected a
declaration" to the other, in the same build. All four are now single
definitions. `Namespace::ALL` is the same fix for the same reason: adding
`Event` corrected one hand-written namespace list and left the other, so an
event was importable and unresolvable depending on which path asked.

### 3. Every graph edge in the corpus pointed at nothing

Resolving policy clauses for the first time found that seven fixtures named
resources and events no file in their program declared. **C2 opened**
(`docs/CORPUS.md`).

A-009 is the one to look at hardest. Its category is "edge materialized menu",
and all four of its edges were dangling — the fixture demonstrated the *syntax*
of a dependency graph and none of its semantics, and it passed C1 because no
analysis had ever read those clauses.

This is the C0 → C1 repair arriving in a second place, and it went unnoticed for
the same reason: a clause nobody resolves cannot be reported as unresolved.

### And once more, in the demo itself

`examples/store/menu.pw` — written *for this milestone*, after all of the above
— named `Store(id), Menu(id)` without importing them. Caught by `PW5100` the
first time the store demo was fed to `pw emit-graph`.

`just ci` had never checked `examples/store/`. It does now. A milestone demo
nothing checks is a milestone demo that can quietly stop being true.

### A fourth, in the graph's own resolution

The page's dependency on its own `query Store` resolved to the **type**
`domain.Store`, because the general `resolve` tries the type namespace first and
`store.page` imports that type. Every page edge pointed at a record definition,
and the graph looked full. Edges now resolve in the three namespaces an edge can
name — term, UI, event — preferring a local declaration over an import.

## The three build-time rules

| code | invariant |
|---|---|
| `PW5100` | a dependency, event or invalidation target must name something the program declares |
| `PW5101` | a shared materialization may only depend on data every reader of its cache entry may see |

`PW5101` is charter §14 M6 gate item 4, decided where the dependency is written
rather than where the bytes are stored. It is **not** covered by `PW5001`: that
rule asks whether a query's own partition admits its data, and in the case
`PW5101` catches every declaration is individually correct. `Cart` asks for a
private cache and gets one; the fragment asks for a shared entry and is entitled
to one. The defect is the edge between them.

Before `PW5101` existed, a `materialize` with `partition public` depending on a
`session query` was accepted.

### `PW5102` was a third rule, and it was ceremony

It required `code_version included_in_key` on every shared materialization,
because a shared entry outlives the deployment that wrote it and markup from
one release hydrated by another is the mismatch E7V refuses in a resume
manifest — except that a cache hit compares nothing, so nothing refuses.

The failure is real. Asking the author to prevent it was the mistake.

> Architect ruling, 2026-08-06: If every shared materialization must be
> separated across incompatible code generations, that is platform mechanism,
> not application policy.

So the **logical key** is the application's — `MenuFragment(store_47)` — and the
**physical storage identity** is the platform's: the materialization, its
privacy partition, the logical key, and a **compatibility generation**. V1 is
the whole build's identity, which is safe and blunt: any deployment invalidates
every fragment. V2 is a per-materialization contract hash, so an unrelated
deployment does not.

`Materializer::new` takes the generation as a **constructor parameter**, and
every read and write goes through `physical()`. The same move as `Authorised` in
E7V: the way to guarantee something is not to check that a caller did it, it is
to leave no way to skip it.

`PW5102` is retired, its number held (`codes::RETIRED`) because a code is a
public identifier and reusing it would make every historical mention describe a
different rule. `code_version included_in_key` still parses and now means
nothing — a program that says something true about the platform is not an
error.

Edge resolution has **no unique-name fallback**, and `Ambiguous` resolves to
nothing rather than to a candidate. E2C deleted by-name resolution from member
lookup for a reason that applies here exactly: whether a dependency exists must
not depend on which spellings happen to be unique across a program.

## The runtime half

`runtime/pw-materialize`, reading the serialized graph — ADR-0018's boundary
applied again, so `pw-core` does not know the materializer exists.

**Losing an event** is the failure this milestone is about, arriving through the
door labelled "reliable messaging". Published after the commit it can be lost
between the two; published before, it can describe a change that rolls back. So
the event and the state change are one transaction in one store (ADR-0019).

**Duplicate delivery** is avoided rather than prevented. An event here is *a
reason to look at the graph*, never *an instruction to regenerate*, so
processing one twice reaches the same conclusion twice and the second
regeneration finds the entry already current. Exactly-once delivery is the
expensive thing, and an idempotent consumer does not need it. The same property
makes out-of-order delivery survivable, which task 8 requires.

**Stampedes** are bounded by admitting one producer per key. The in-flight set
is cleared by a drop guard rather than at the end of the happy path, because a
producer that panics would otherwise strand its key and every later reader of
that entry would wait forever.

A **failed regeneration leaves the last good entry in place**. Clearing it would
turn a servable stale page into a missing one, so an origin blip would become an
outage — through the code meant to handle origin blips.

| 2 | duplicate events are harmless | **PASS** — two events naming one entry coalesce to one invalidation; a third after regeneration finds it current |

## Every number has its negative control

The pattern `docs/RISK_QUEUE.md` exists to enforce, applied here deliberately,
because "1 of 1000 regenerated" is exactly the shape of a favourable number that
measures nothing.

| claim | what makes it mean something |
|---|---|
| 1 of 1000 regenerated | the same fixture with an argument-less event regenerates 1000 |
| 999 untouched | counted from the causality record, not from freshness — the one that *did* regenerate is fresh again afterwards, so counting fresh entries reports 1000 untouched and calls it a pass |
| 8 readers, 1 producer call | the same test with `single_flight` off produces more than once |
| the fragment listens for `MenuChanged` | it does not listen for `CartChanged`, asserted beside it |
| the committed graph JSON | regenerated and compared by a `pw-cli` test, so a renamed field fails a test instead of ageing a fixture |
| a rolled-back command emits nothing | a committed one emits something — otherwise both hold for a `command` that never writes |

## What is not claimed

**SQLite is not the production store** (ADR-0019). It is a transactional store
that runs in a test with no service to start, which is what makes the
failure-injection matrix runnable: a crash between the state write and the
commit is a `panic!` between two statements.

**The materializer is behaviour, not a guarantee** — the same standing as
`pw-tasks` (ADR-0016). A passing test here does not make misuse a compile error.
The compile errors are `PW5100`, `PW5101` and `PW5102`.

**Regeneration produces a string.** What a fragment's body actually *is* — the
rendered markup — belongs to E7's renderer. What E6 owns is when it is produced,
what it is keyed by, and what it is allowed to read.

**Cache-key auditing is in `pw explain`** — task 9, landed as a follow-up on the
architect's ruling of 2026-08-06 rather than deferred into E7: the computation
existed, `explain` did not surface it, and E6 had just finished demonstrating
how dangerous unread policy information is.

It reports the logical key, the automatic platform dimensions, the application
dimensions, and any **potential key gap**: a dependency that separates its
entries by something this key does not, so one document serves every value of
it. Advice rather than a diagnostic, because two readers sharing an entry is
sometimes exactly what a cache is for and the compiler cannot tell that from a
mistake.

The build generation is deliberately absent from the application section. That
is what `PW5102` used to ask for, and it is injected now.
