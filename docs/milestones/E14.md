# E14 — The AI benchmark (and the tooling it needs)

**Status: started 2026-10-02**, ahead of E11-E13 by ruling (ADR-0119).

## Question

> Does the new language materially improve human review and AI coding
> reliability compared with React and contemporary alternatives?
> (charter §14 M14)

The claim under test is narrower than "agents like Pleris": **an invalid
change that compiles in React/Next or SvelteKit is refused by `pw check`, and
the refusal leads an agent to a correct change in fewer, cheaper attempts.**
The result may also be that it does not. The benchmark has to be able to say
either, so a negative result is a finding, not a failure.

## Gate (charter §14 M14, unchanged)

1. Semantic diffs are generated for the store app.
2. At least 10 benchmark tasks exist across all three stacks.
3. The evaluation is reproducible and does not expose hidden tests.
4. Results distinguish model capability from harness effects.
5. The project can state with evidence which bug classes became
   unrepresentable.

## Shape

```text
benchmarks/                         (charter §12)
  baselines/{next-react,sveltekit}/ the store in Next.js and SvelteKit; Pleris's is examples/store
  harness/contract/                 the shared behavioural contract (E14-A, ADR-0120)
  tasks/T01-.../
    prompt.md                       the request, identical across stacks
    hidden/{next,sveltekit,pleris}/ grading tests the agent never sees
    reference/{...}/                a known-good patch per stack
  harness/                          isolate, run agent, grade, record
  results/                          one JSON per (model, stack, task, seed)
```

- **One behavioural test suite across stacks.** The three stores serve the
  same routes and markup contract, so one Playwright suite grades all three.
  Each stack adds its static checks (`tsc`/ESLint/svelte-check; `pw check`).
- **Grading is deterministic** (task 6): tests and checkers only, no LLM judge.
- **Hidden means hidden** (gate 3): the agent's sandbox is a copy of the
  baseline with no `hidden/` or `reference/` directory, and the harness
  checks that.

## Admissibility (the project's rule applied to a benchmark)

A score is evidence only if its instrument has shown it can tell good from
bad, per task and per stack:

| control | must hold |
|---|---|
| negative | the unmodified baseline FAILS the hidden tests |
| positive | the reference patch PASSES the hidden tests |
| unsafe | a plausible wrong patch (e.g. the cart cached shared) FAILS, by test or by checker |
| harness | a no-op agent scores 0; a replay of the reference patch through the agent path scores 1 |

The "unsafe" row is where the thesis lives: for each task, which stack
catches the wrong patch, and at what stage (type check, `pw check`, test,
or not at all). That table is gate item 5.

**T12's unsafe control on Pleris.** The plausible wrong fix moves the cart into
a `public` query with `consistency snapshot` and keeps `cache shared`. Until
2026-10-02 it checked clean and scored 1: the checker did not read what a
query is given, and accepted a reader's value in a shared cache keyed by the
reader. ADR-0128 closed both; `pw check` now refuses it (PW5001, naming the
parameter `session`). At run time the server keys the entry by its session
since ADR-0127, so the hidden tests could not see it: on Pleris the checker is
what grades this task.

**T11's unsafe control on Pleris.** The plausible wrong fix shows the dialog
from an "open" state and does not hear Escape close it: the state still says
open, and Clear cannot open it again. In Next.js and SvelteKit (`useState`
or `$state` with an effect calling `showModal`) it builds, and only the
hidden test that presses Clear after Escape fails it. In Pleris the same
patch, a `<dialog>` a signal shows with no `close` handler, is refused by
`pw check` (PW5303) before any test runs.

**T03's unsafe control.** The plausible wrong fix keeps the cart's lines
between requests, to save computing them, forgets them when a cart changes,
and keys them by the store alone. With one customer at a time, every test of
the list passes. Next.js and SvelteKit build it, and the hidden test with a
second customer fails it: the second sees the first one's cart. In Pleris the
same intent is the lines' query cached `shared`, and `pw check` refuses it
(PW5001, ADR-0128) before any test runs.

**T04's unsafe control.** The order feature is T04's setup patch on each
stack: a status the kitchen sets, shown in the store's order section. The
plausible wrong fix adds the new state, ready for pickup, and forgets to show
it. In Next.js and SvelteKit the baseline shows each state in the
framework's common idiom, a JSX conditional or an `{#if}` chain. Both build
the wrong fix, the page shows nothing for a ready order, and only the hidden
test fails it. In Pleris the section is a `{#match}`, and `pw check` refuses
the wrong fix: `` `{#match status}` does not cover `Ready` `` (PW0305).

**T06's unsafe control on Pleris.** The plausible wrong form names its
field with a placeholder: the field has an `id` and no label, and its error
is neither tied to the field nor announced. Next.js and SvelteKit build it,
and the hidden tests that find the field by its label fail it. In Pleris it
passed `pw check` too, until writing this task found why: PW5014 took any
`id` as a name. ADR-0143 corrected the rule. `pw check` now refuses the
patch, and the note says "no `<label for="request">` in `StorePage` names
this `id`".

**T05's unsafe control.** The recommender takes over a second. The
plausible wrong fix waits for it before the page is sent:
- Next.js: `await getRecommendations()` in the page;
- SvelteKit: `await` in its `load`.

Both build. The page then arrives whole once the recommender has answered,
and only the hidden test that presses Add while the recommendations are
pending fails it. In Pleris the setup declares the recommender's query
`delivery streamed`, and `pw check` refuses the `let` that waits for it
(PW5400, since ADR-0148).

The reference streams the section, in each framework's form:
- Next.js: `<Suspense>` around an async component;
- SvelteKit: an unawaited promise from `load`, shown with `{#await}`;
- Pleris: a `<stream>`.

**T10's unsafe control.** The store shows the session's delivery estimate.
The estimator is slow, and sometimes it is down. In the setup the page waits
for the estimate and fails with it. The plausible wrong fix adds the loading
state and forgets the failure:
- Next.js: `<Suspense>` with no error handling. A failed estimate replaces
  the whole page with "This page couldn't load", answered 200, with no menu.
- SvelteKit: `{#await}` with no `{:catch}`. The menu stays, and the Delivery
  section goes blank.

Both build, and only the hidden test with a failing estimator fails them. In
Pleris the same patch is a `<stream>` with no `<failed>`, and `pw check`
refuses it (PW5401, since ADR-0148).

Writing T10 found that `pw-render --plan`, the static render inside a
Pleris build, had no value for a private query's text part. The store's
cart count is given one by the values file; the estimate had none, so T10's
setup did not build. That render is no session's, and now shows nothing of a
session's value, as it renders a private list empty and a private block as
nothing (ADR-0145, ADR-0147).

**T09's unsafe control.** The store shows the notice it has posted. Asking
the notice board is expensive, so the setup keeps its answer five minutes.
The task: a new notice shows within ten seconds, and the board is still asked
at most once in ten seconds. The plausible wrong fix stops keeping the
notice: `freshness 0.seconds` in Pleris, a zero time-to-live elsewhere. Every
stack builds it, Pleris's included, and only the hidden test that counts the
board's calls fails it.

This is the table's honest row. How long a value may be kept is a product
decision, and no checker can know the right one. What Pleris gives the
reviewer is the decision as one declared line. `pw diff` reports the
reference as one change, `` `store.page.Notice`: `freshness` is
`5.seconds`, was `5.minutes` ``, and the unsafe patch as the same line with
`0.seconds`.

**Writing T09 found that a Next.js cache's freshness is not its own.** The
first Next.js setup kept the notice with `unstable_cache` and a five-minute
`revalidate`, and its negative control failed: the unchanged store passed the
hidden tests. The cart's server actions call `revalidatePath` for the store's
page, as the store's contract needs. In Next.js 16.3.8, `unstable_cache`
reads an entry under the implicit tags of the route rendering it, and a
revalidated path expires every entry read under its tag
(`dist/server/web/spec-extension/unstable-cache.js` passes them as
`softTags`; `incremental-cache/file-system-cache.js` misses on them). So any
press of Add refreshed the notice: the cache's freshness was whatever the
page's other actions made it. The setup keeps the notice in a module-level
map instead, as SvelteKit's does, which `revalidatePath` does not reach. In
Pleris a query's freshness is declared on the query, and a command
invalidates only the queries it names.

A blocked task stays in the set and is reported as "not expressible", which
is itself a result about the language.

## Slices, in order

1. **E14-A, the Next.js and SvelteKit stores.** Done 2026-10-02 (ADR-0120,
   `just e14-contract`). The canonical store
   (charter §15) at feature parity with `examples/store`, plus the shared
   Playwright suite all three pass. Versions verified against primary sources
   and pinned.
2. **E14-B, the harness, offline.** Done 2026-10-02 (ADR-0124), with T08. Isolation, grading, result JSON, and the
   four controls, exercised with the no-op agent and reference replay only.
   No model is called.
3. **E14-C, the tasks.** T01-T12 with prompts, hidden tests, reference
   patches and unsafe patches, every control green per stack. Gate items 2
   and 3. Ten are written as of 2026-10-03, which gate item 2 asks for; T02
   and T07 remain.
4. **E14-D, the semantic diff for the store** (gate item 1). Done 2026-10-03
   (ADR-0149, `just e14-diffs`): `pw diff` over two checked programs,
   reporting effects, capabilities, privacy, placement, cache, invalidation
   and client bytes, in charter §19.2's sections. The evidence is its report
   over every task's Pleris reference and unsafe patch.
5. **E14-E, agent runs**: models x stacks x tasks x seeds, recording pass@1,
   compiler iterations, behavioural and static-safety failures, changed lines,
   tokens, cost and latency. Gate item 4 is a design question here (below).
6. LSP and causal devtools (tasks 1-2) are not gate items and come after.

## Decisions the owner holds (charter §3.2: expensive or needing credentials)

1. **Which models and agents**, and the budget. E14-E calls paid APIs, or
   local models for the roadmap's "small model" demo. Nothing is called
   before this is decided.
2. **How Pleris is taught to an agent.** No model has seen Pleris. Options:
   the language reference in context, a fixed tool to read the docs, or both.
   React gets nothing extra. This is the main harness effect gate item 4 must
   separate from capability.
3. **Whether a "not expressible" task counts as a Pleris failure** in the
   headline number, or is reported beside it.
