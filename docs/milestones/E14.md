# E14 — The AI benchmark (and the tooling it needs)

**Status: started 2026-10-02**, ahead of E11-E13 by ruling (ADR-0119).

## Question

> Does the new language materially improve human review and AI coding
> reliability compared with React and contemporary alternatives?
> (charter §14 M14)

The claim under test is narrower than "agents like Pleris": **an invalid
change that compiles in React/Next or SvelteKit is refused by `pw check`, and
the refusal leads an agent to a correct change in fewer, cheaper attempts.**
The result may also be that it does not. The benchmark has to be able to say
either, so a negative result is a finding, not a failure.

## Gate (charter §14 M14, unchanged)

1. Semantic diffs are generated for the store app.
2. At least 10 benchmark tasks exist across all three stacks.
3. The evaluation is reproducible and does not expose hidden tests.
4. Results distinguish model capability from harness effects.
5. The project can state with evidence which bug classes became
   unrepresentable.

## Shape

```text
bench/
  stacks/{next,sveltekit,pleris}/   the same store, three times (baseline repos)
  tasks/T01-.../
    prompt.md                       the request, identical across stacks
    hidden/{next,sveltekit,pleris}/ grading tests the agent never sees
    reference/{...}/                a known-good patch per stack
  harness/                          isolate, run agent, grade, record
  results/                          one JSON per (model, stack, task, seed)
```

- **One behavioural test suite across stacks.** The three stores serve the
  same routes and markup contract, so one Playwright suite grades all three.
  Each stack adds its static checks (`tsc`/ESLint/svelte-check; `pw check`).
- **Grading is deterministic** (task 6): tests and checkers only, no LLM judge.
- **Hidden means hidden** (gate 3): the agent's sandbox is a copy of the
  baseline with no `hidden/` or `reference/` directory, and the harness
  checks that.

## Admissibility (the project's rule applied to a benchmark)

A score is evidence only if its instrument has shown it can tell good from
bad, per task and per stack:

| control | must hold |
|---|---|
| negative | the unmodified baseline FAILS the hidden tests |
| positive | the reference patch PASSES the hidden tests |
| unsafe | a plausible wrong patch (e.g. the cart cached shared) FAILS, by test or by checker |
| harness | a no-op agent scores 0; a replay of the reference patch through the agent path scores 1 |

The "unsafe" row is where the thesis lives: for each task, which stack
catches the wrong patch, and at what stage (type check, `pw check`, test,
or not at all). That table is gate item 5.

## Tasks (the charter's seven, plus the roadmap's)

| id | task | likely Pleris status today |
|---|---|---|
| T01 | add an optimistic cart update (with rollback) | expressible |
| T02 | fix a duplicate request storm | expressible (`concurrency one_per_key`) |
| T03 | add a private resource without a cache leak | expressible (PW5001/5004/5101) |
| T04 | add an order-state variant | expressible (exhaustive match) |
| T05 | stream recommendations | partial: `<stream>` refused by name (ADR-0075) |
| T06 | make a form accessible | blocked: event as handler parameter (ADR-0058) |
| T07 | cancel a stale navigation request | expressible (`on_key_change cancel`) |
| T08 | prevent duplicate submissions | expressible (`idempotent_by`) |
| T09 | change cache freshness | expressible |
| T10 | add a loading/error state | expressible (`{#match}` over `Result`) |
| T11 | add an accessible dialog | blocked: view composition (ADR-0072) |
| T12 | repair an intentionally unsafe patch | expressible |

A blocked task stays in the set and is reported as "not expressible", which
is itself a result about the language.

## Slices, in order

1. **E14-A, the Next.js and SvelteKit stores.** The canonical store
   (charter §15) at feature parity with `examples/store`, plus the shared
   Playwright suite all three pass. Versions verified against primary sources
   and pinned.
2. **E14-B, the harness, offline.** Isolation, grading, result JSON, and the
   four controls, exercised with the no-op agent and reference replay only.
   No model is called.
3. **E14-C, the tasks.** T01-T12 with prompts, hidden tests, reference
   patches and unsafe patches, every control green per stack. Gate items 2
   and 3.
4. **E14-D, the semantic diff for the store** (gate item 1): `pw diff` over
   two checked programs, reporting effects, capabilities, privacy,
   placement, cache, invalidation and client bytes.
5. **E14-E, agent runs**: models x stacks x tasks x seeds, recording pass@1,
   compiler iterations, behavioural and static-safety failures, changed lines,
   tokens, cost and latency. Gate item 4 is a design question here (below).
6. LSP and causal devtools (tasks 1-2) are not gate items and come after.

## Decisions the owner holds (charter §3.2: expensive or needing credentials)

1. **Which models and agents**, and the budget. E14-E calls paid APIs, or
   local models for the roadmap's "small model" demo. Nothing is called
   before this is decided.
2. **How Pleris is taught to an agent.** No model has seen Pleris. Options:
   the language reference in context, a fixed tool to read the docs, or both.
   React gets nothing extra. This is the main harness effect gate item 4 must
   separate from capability.
3. **Whether a "not expressible" task counts as a Pleris failure** in the
   headline number, or is reported beside it.
