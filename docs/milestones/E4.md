**Status: COMPLETE.** All seven gate items pass.

Was: five of seven. Since ADR-0018 the compiler
and the runtime are connected by the resource manifest; what the two open items
still need is a *page*, and something that decides **when** to run a resource
rather than only how it behaves.

### Why item 1 is not met, precisely

**The compiler and the runtime are now connected** — ADR-0018 made the resource
manifest a serialized artifact, `pw emit-manifest` produces one for all seven
accepted-corpus resource declarations, and
`runtime/pw-resource/tests/from_manifest.rs` proves a policy written in `.pw`
governs runtime behaviour: edit `freshness 30.seconds` to `5.seconds`,
regenerate, and the cache boundary moves.

What is still missing is **when to run**, not **how to behave**. A host still
writes the fetch itself; nothing generates the call. A store demo therefore
remains a hand-written application that uses the runtime, and the part it would
demonstrate — that the language drives it — is exactly the part that does not
exist. That is E6's, alongside the materialized resource graph.

### What is deliberately not built

**SQLite (task 6).** The cache is in memory. Every gate property above is about
identity, lifetime and concurrency, none of which a storage engine changes. It
is real work, not a shortcut, and it belongs with the store demo.

**Streamed recommendations (task 7).** These are what E3 gate 3 waits on. They
need the generator too: a streamed region is a resource whose value is not ready
yet, and there is no way to express that in `.pw` today.

**Causal traces from click to DOM part (task 12).** `Trace` records what the
runtime did, which is the substrate. Joining it to a DOM part needs the
renderer's part identity, which is E7.

## What implementing it found

**A test clock is not a convenience.** Freshness, timeout and backoff are all
time. Sleeping for them makes a suite slow and flaky, and a flaky concurrency
suite gets muted rather than fixed. Every timing property here is exact because
the test owns the clock — and the suite ran 20 consecutive times with zero
failures.

**Jitter and determinism are not in conflict.** Retry jitter exists so a herd
does not retry in lockstep. Deriving it from the *key* rather than from
randomness keeps it spread across keys while staying exactly predictable, so a
test can assert on it. Asserted both ways: two keys differ, one key repeats.

**A cache is unusually good at looking correct.** It returns the right answer
whether or not it did the right thing, so every test here has a control that
fails if the runtime cheats — a freshness test that would pass on a cache that
never expires, a privacy test that would pass on a runtime that simply refuses
to cache private data, a dedup test that would pass on a global lock.
