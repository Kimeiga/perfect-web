# E2 — Source language front end

**Status: PARTIAL.** Three of six gate items pass. The remaining three need
lowering to Koka and a formatter, neither of which exists.

## Question

> Can the project expose a much smaller, clearer, Svelte-like application
> language while delegating initial value/effect checking to Koka?

**Answered so far: the language can be *read*.** All 68 corpus files parse, with
precise spans and error recovery. Whether it can be *lowered* is untested.

## Gate

Charter §14 M2 lists six items.

| # | gate item | result |
|---|---|---|
| 1 | `pw check examples/accepted/hello.pw` succeeds | **PASS** — succeeds on all 68 files |
| 2 | ≥40 rejected examples report errors at original `.pw` spans | **FAIL** — see below |

### Why gate item 2 fails, stated precisely

The 44 rejected corpus files **parse cleanly**, and that is correct: they are
syntactically valid programs that violate *semantic* rules. `R-001` (a network
request inside a view) is well-formed `pw`; what makes it wrong is the effect
row, and no pass yet reads effect rows against a rule.

So E2 has built the thing that *carries* spans to a diagnostic, and E1/E1A/E5
own the rules that produce them. `pw-core` already has five checkers
(exhaustiveness, nominal types, ABI decoding, scope escape, capability audit)
with 42 passing tests — **they are simply not wired to the parser yet.**

That wiring is the next task and it is small: walk the parsed AST, build
`pw-core`'s `Program`, and run the checkers. It is listed as the top item in
`docs/NEXT.md` rather than claimed here.

## What building this found

**Thirteen corpus files were malformed.** Every `query`/`command` declaration I
wrote had a spurious `{` after the signature, opening a policy block that was
never closed — three opens against two closes. Charter §8.1 writes policy
clauses *unbraced* between the signature and the body. `corpus-check` could not
see it because it only reads the `// @` header, and no other tool read the
files at all.

**Three grammar gaps, all found by parsing the corpus rather than by design.**
The unit type `()` as a return type, effect rows on `paint`-shaped declarations,
and module-level `let` bindings. None were exotic; all three appear in files
written before the parser existed. Fixture tests would not have found any.

**The lexer needed a `#` token**, because the corpus writes Svelte-style
`{#each}` template blocks. Caught by the "no Unknown tokens in the corpus"
property, which is treated as a failure rather than tolerated — in a
specification corpus, an unknown byte means the grammar is missing something.

## Deliberate non-goals at this milestone

- **Expression and template bodies are not parsed.** They are captured as
  balanced token ranges. E2's gate is declarations, spans and recovery;
  parsing expressions we cannot yet check would grow the test suite while
  proving less.
- **Policy clauses are not interpreted.** Their grammar differs per keyword and
  E4 owns their meaning. They are captured as normalised text plus a span.
- **`pw fmt` is not shipped.** The lexer is lossless so it is *possible*, but an
  idempotent formatter needs a decision about the canonical declaration layout,
  and reflowing 68 corpus files into a shape nobody agreed on would be worse
  than not having it.

## Open

The **lossless tree** question ADR-0009 left open is still open. The current
design keeps a gap-free token stream plus a declaration AST that references
spans — enough for `fmt` to round-trip, not yet a red/green tree. `rowan` 0.17.0
remains the recorded candidate if E9's incremental queries need one.

## Next decision

Wire `pw-core`'s five checkers to the parsed AST. That converts 44 rejected
corpus files from "parses fine" into real compile failures and moves gate item 2
from FAIL to a measurable number.
