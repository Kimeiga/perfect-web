## Question

> Can the project expose a much smaller, clearer, Svelte-like application
> language while delegating initial value/effect checking to Koka?

**Answered so far: the language can be *read* in full.** All 68 corpus files
parse to a lossless tree — declarations *and* bodies — with precise spans and
error recovery. Whether it can be *lowered* is untested, and that is now the
only thing standing between the corpus and the checkers already written.

### Gate item 4: executing through Koka

`pw emit-koka` lowers the **pure subset** (ADR-0015) and
`spikes/pw-to-koka/run.sh` compiles and runs it with the pinned Koka 3.2.3:

```text
line_total=750          3 * 250
with_delivery_near=1049 750 + 299 + 0
with_delivery_far=1249  750 + 299 + 200
label_draft=draft
label_confirmed=ORD-42
```

Every expected value was computed by hand from the source, not from a previous
run. Two negative controls run alongside: a wrong expectation must be caught by
the same comparison, and a **non-exhaustive match must be rejected**. The second
matters — every generated function declares `total`, and Koka's rejection reads
`type error: effects do not match`, which is E0 finding F-8's mechanism
confirming the annotation is load-bearing rather than decorative.

**What this does not show**, per ADR-0015: nothing about nominal types (F-4
measured that Koka erases them), nothing about the effect system (only `!{}`
functions lower), and nothing about Koka being the eventual backend. Across
`examples/accepted/`, far more declarations are skipped than emitted, and a test
asserts that ratio so the subset cannot quietly appear larger than it is.

### The ≥40 figure moved, and why

The original wording — "at least 40 rejected examples report errors" — is an
**E9 property wearing an E2 label**. Of the 25 files E2 does not catch, roughly
15 need effect inference, 3 need type checking, 2 need affine types, 2 need
serialization analysis and 1 needs whole-program reachability. Two are reachable
with what E2 and E5 own.

A gate that cannot be met by its own milestone's work makes the register
meaningless: E2 would read "in progress" for six milestones after its work was
finished. The architect retargeted it to **ownership** and moved the numeric
threshold to a cross-milestone **P0 readiness gate**:

```text
P0 readiness gate
- At least 40 of 44 rejected corpus programs are source-level compile errors.
- Every headline P0 invariant has at least one enforced fixture.
- Every accepted program remains free of error diagnostics.
- Every rejected program fails for its declared invariant.
- Every effect family has direct, helper-hidden and callback-hidden coverage.
```

**21 is not a permanent threshold.** It is today's consequence of the corpus
ownership map, and it moves as E2B, E2C and E2D land. Long-term the target is
44/44; 40/44 is a *publication* threshold, not a frontend one.

### Why gate item 2 is 4 of 44, stated precisely

All 44 rejected files **parse cleanly**, and that is correct: they are
syntactically valid programs that violate *semantic* rules.

Nine declaration-level rules now run (`compiler/pw-cli/src/rules.rs`) and catch
four of them:

| file | code | rule |
|---|---|---|
| R-014 | `PW0312` | retry of a non-idempotent command |
| R-015 | `PW0313` | unbounded retry |
| R-027 | `PW0325` | keyed query with no stale-work policy |
| R-029 | `PW0327` | optimistic transition with no rollback |

One more comes from the body, through HIR:

| file | code | detector | rule |
|---|---|---|---|
| R-007 | `PW0305` | `pattern_matrix` | match on `OrderState` is not exhaustive |

R-007 is the first case caught by an algorithm rather than by a declaration
rule. `compiler/pw-core/src/check.rs` builds a type environment from every file
in the invocation (assumption A-009), lowers each body, and runs the
usefulness algorithm from `exhaust.rs` on each `match` whose scrutinee type is
known. The diagnostic carries the match span, the scrutinee span, and the five
missing variants by name, including `Cancelled(CancellationReason)` — the exact
string R-007 declares it expects.

The bridge is deliberately unable to guess: a `match` whose scrutinee type is
not declared is skipped in silence rather than reported with an assumed type.

The other 40 need one of three things E2 does not have:

- ~~**body parsing**~~ — **removed as a blocker.** `grammar.rs` now parses
  every body, including the ones that carry the violation: `R-001` (a network
  request inside a view) and `R-004` (a session query in a shared-cached `page`
  body) are real expression trees, not unparsed token ranges. What is still
  missing is the step *after* parsing — see HIR below;
- **HIR lowering** — the rules in `pw-core` consume ids and spans, not syntax
  nodes (ADR-0012). Until bodies lower, the tree the grammar produces cannot
  reach the checkers that are already written and tested;
- **effect checking** — E1 owns whether a declared row is *satisfied* by a body;
- **privacy and placement solving** — E5.

The honest statement of the gap: the checkers exist and pass 62 tests, the
bodies now parse, and **nothing connects them**. That single missing link is
worth more than any further rule work.

Coverage is ratcheted by `rules::corpus_tests` so it cannot silently regress.

## What building this found

**Thirteen corpus files were malformed.** Every `query`/`command` declaration I
wrote had a spurious `{` after the signature, opening a policy block that was
never closed — three opens against two closes. Charter §8.1 writes policy
clauses *unbraced* between the signature and the body. `corpus-check` could not
see it because it only reads the `// @` header, and no other tool read the
files at all.

**Three grammar gaps, all found by parsing the corpus rather than by design.**
The unit type `()` as a return type, effect rows on `paint`-shaped declarations,
and module-level `let` bindings. None were exotic; all three appear in files
written before the parser existed. Fixture tests would not have found any.

**The lexer needed a `#` token**, because the corpus writes Svelte-style
`{#each}` template blocks. Caught by the "no Unknown tokens in the corpus"
property, which is treated as a failure rather than tolerated — in a
specification corpus, an unknown byte means the grammar is missing something.

## Deliberate non-goals at this milestone

- **Expression and template bodies are not parsed.** They are captured as
  balanced token ranges. E2's gate is declarations, spans and recovery;
  parsing expressions we cannot yet check would grow the test suite while
  proving less.
- **Policy clauses are not interpreted.** Their grammar differs per keyword and
  E4 owns their meaning. They are captured as normalised text plus a span.
- **`pw fmt` is not shipped.** The lexer is lossless so it is *possible*, but an
  idempotent formatter needs a decision about the canonical declaration layout,
  and reflowing 68 corpus files into a shape nobody agreed on would be worse
  than not having it.

## Open

The lossless-tree question is **closed** — ADR-0012 adopted `rowan` 0.17.0, and
the green tree, tag space and both losslessness suites are in place. All 68
corpus files round-trip through the tree.

Still open within E2: porting the parser to emit into the tree, the core body
grammar (expression and pattern kinds are reserved but unfilled), HIR lowering,
and `pw fmt` (ADR-0013, deliberately deferred until the syntax/HIR boundary
stabilises).

## What wiring the rules found

**The implementation invented its own error codes.** The corpus had already
declared them in `@rule` headers. The corpus is the specification, so the codes
were changed to match it. `every_caught_rejection_matches_its_declared_rule`
now enforces that a file is caught by the rule it *declares*, not merely by
something — otherwise a checker could pass by rejecting for the wrong reason.

**Two accepted files then failed.** A-003 and A-004 are keyed queries that never
declared `on_key_change`, which is precisely what R-027 rejects. The accepted
corpus did not comply with its own specification. A false positive on a program
the corpus calls correct is worse than a miss, so
`no_accepted_corpus_file_produces_an_error` is the first assertion in the suite.

## Next decision

Parse function and template bodies. That is what unlocks the largest block of
the rejected corpus — the effect-in-view family (`R-001`, `R-033`, `R-036`,
`R-037`) and the body-level policy violations (`R-004`) — and it is what E1's
lowering will need anyway. The `R-037` case (an effect smuggled through a
generic callback) is the one that matters most: RQ-2 proved the backend
propagates effects that way, and the `pw` checker must be shown to do the same.
