# ADR-0159: a handler handles what its command answers

Status: accepted under the owner's delegation of 2026-10-02. Date: 2026-10-03.
Milestone: E14. What ADR-0157 left open: a handler can read what its command
answered, and nothing made it.

## Context

1. **ADR-0099 let a handler drop a failure.**
   - It refuses a `Result` that nothing uses (PW0618).
   - It counted a lambda's body as used, "its caller's to use", and said: "A
     handler's command answer is the runtime's to drop".
   - That was all a handler could do then, since it was answered nothing.
2. **ADR-0157 answers a handler what its command did**: `Result<(), E>`, with
   the error the command declares if it did not commit. The runtime still
   drops a handler's value. So `=> clear_cart()` drops a refusal without a
   word, and the press looks as though it worked.
3. **The same failure was judged three ways.**
   - Dropped as a statement, `{ clear_cart() \n note = "" }`, it was refused
     (PW0618).
   - As the handler's last value, `=> clear_cart()`, it checked and
     compiled.
   - Handed on by `?` or by `return`, it checked, and the backend refused it:
     "blocked upstream: `?` on a Result in a function returning Unit; the
     checker refuses it". The checker did not.
4. **The discard ADR-0099 prescribes could not end a handler.**
   `{ let _ignored = clear_cart() }` checked. The backend refused it as "a
   block ending in a binding".
5. **Charter §15.6 test 10 was met because the store chose to match.** Even
   so:
   - its Add handler's catch-all, `_ => notice = ""`, hid every refusal but
     "sold out";
   - its Clear handler dropped its answer.

## Decision

1. **A handler's value goes to the runtime, which drops it.** So PW0618
   refuses a `Result` a handler gives the runtime, as it refuses a
   statement's. That covers three things:
   - its body's last value;
   - a value it `return`s;
   - the failure a `?` in it returns.

   A lambda inside a handler is an ordinary lambda: its value, and its `?`,
   belong to its caller.
2. **A handler takes the answer apart with `match`, or discards it by name**,
   `let _ignored = ..`. Either is a decision a reviewer and `pw diff` can see.
   - A block ending in a binding is now the unit value wherever no other
     value is wanted, so the discard compiles.
   - A handler that discards its call's answer is named for the call, as one
     that matches on it is.
3. **The canonical store shows every refusal.**
   - Add: "That item just sold out." for `ItemUnavailable`, and "That item
     could not be added." for any other error.
   - Clear: "The cart could not be cleared."
4. **Where nothing is to be shown, the answer is discarded by name:**
   - the pick demo, whose command never refuses;
   - the benchmark's store, whose behaviour and parity with the other two
     stacks are unchanged.

   T11's two patches carry those lines, and are regenerated by git from the
   old trees, transformed. Every task's Pleris patches check as before.

## Alternatives

- **Leave it to the runtime**, for example by marking a button whose handler
  returned an `Err`. The press would fail visibly, but not in words the
  product chose, and a declared error is a case the program knows about.
  Others:
  - React's error boundaries do not catch event handlers' errors.
  - typescript-eslint's `no-floating-promises`, in its recommended
    type-checked rules, flags a promise nothing handles, and takes `void` as
    the explicit discard.
  - Elm returns an HTTP request's `Result` to `update`, whose `case` covers
    `Ok` and `Err`.

  Pleris takes the last two: a failure the program declares is handled
  where it arrives, or dropped by name.
- **A warning.** PW0618 is an error for a statement, and the failure is the
  same.
- **Refuse only `?` and `return` in a handler.** That closes the two forms
  the backend refused, and leaves open the one that compiled.

## Acceptance

- `compiler/pw-core/tests/results_handled.rs`:
  - a handler's last value, a `return` and a `?` that give the runtime a
    `Result` are each refused, with their own message;
  - the controls check with no diagnostic at all: a `match`, a discard by
    name, a handler setting a signal, and a lambda inside a handler whose
    `?` returns to its caller.
- `compiler/pw-core/tests/handlers.rs`:
  - the store's Add and Clear handlers, run under Node, show each refusal;
  - a discard by name compiles, sends its command, and is named for it;
  - a block ending in a binding where a value is wanted is still refused.
- These check clean:
  - the canonical store with its demos;
  - the benchmark's store;
  - kiokun;
  - every task's Pleris reference.
- Every task's unsafe patch is refused by the same rules as before.
- The browser suite, in three engines.
- `scripts/handler_failures_mutations.py`: 6 mutants. ADR-0099's 7 are
  re-anchored on the walk this rewrote. Both are recorded by
  `just e14-handler-failures`.
- Every task's four Pleris controls: `just e14-pleris-controls`.

## Not claimed

- **A named function bound as a handler**, `on:submit={save}`, is checked
  against its event (PW0602) and not compiled. Its result is not yet held to
  this rule.
- **No browser test makes the server refuse a clear.** The compiled Clear
  handler's reaction is tested under Node, and the server's refusal path is
  tested for Add.
