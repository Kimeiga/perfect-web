# ADR-0176: a regeneration that fails sends nothing, and is tried again

Status: accepted under the owner's delegation of 2026-10-02. Date: 2026-10-04.
Milestone: E14, the audit's sixth gap (charter §15.5): a materializer
failure, which was injected only in `pw-materialize`'s own tests.

## Context

Measured on 2026-10-04, with this ruling's control and the drain as it was.
A session's next regeneration of its cart's entry failed, once. The page
pressed Add Espresso, then Add Cortado, and showed one line where two were
right, with no error and no reload (`e2e/materializer.spec.mjs`). The code
says why:

- **A failed regeneration's frames were still sent**, at the version that
  had not moved. The page ignores a patch that advances nothing, while the
  server recorded the page as showing it. Its next patch was derived from a
  document the page did not have.
- **The commit's answer named that version.** The page took the value it
  held to include the press, and dropped the line it had shown.
- **The stale entry was never tried again.** The materializer reports an
  entry as invalidated only when it was current, so a session whose
  regeneration failed was not regenerated by the drains after it.

`pw-materialize` keeps a failed regeneration's entry, stale, and says so
(`Regenerated::Failed`). The server did not look.

## Decision

1. **`POST /bench/materializer?fail=next`: a materializer failure.** The
   session's next regeneration of its cart's entry fails. Once.
2. **A regeneration that fails sends nothing.** The entry stays stale, and
   the page keeps what it shows.
3. **A stale entry is regenerated at the session's next drain**, and its
   change sent. A page's subscription request drains its session first, so
   the change reaches the page within one subscription.
4. **The commit's answer names the version the regeneration was tried at.**
   Any regeneration after it passes that version, so the page keeps its line
   until the value that includes the press comes (ADR-0122, ADR-0172).

## Alternatives

- **Tell the page to reload.** It would read the page again for a failure
  the server can recover from alone, and lose what the page holds.
- **Retry inside the drain, with backoff.** The command would wait on it.
  The page asks again on its own schedule, and a session no page reads is
  not regenerated for no reader.
- **Leave the version out of the answer.** The runtime reads a commit with no
  version as one its value already includes, and drops the line.

## Acceptance

Recorded by `just e14-materializer-failure` in
`docs/evidence/E14/materializer-failure.txt`:

- The development server's test, the failure armed through its control: a
  commit whose regeneration failed sends nothing and leaves the version
  where it was, and its answer names a version a later one passes. The
  session's next drain sends the change once, at a version past it.
- `e2e/materializer.spec.mjs`, in Chromium, Firefox and WebKit: after a
  failed regeneration, the press is reconciled by the server's value, the
  next one too, and the page shows two lines, without a reload or a refused
  patch. It failed in Chromium before this ruling, one line short.
- `scripts/materializer_failure_mutations.py`: 6 mutants.

## Not claimed

- **A regeneration that fails every time.** The page keeps its speculation,
  and each of its subscription requests tries again: nothing bounds that but
  the page's own pace.
- **Why a retried regeneration happened.** It records no outbox id
  (`because`), as the first materialization records none.
