# ADR-0164: a menu change drops what declares it, for its store

Status: accepted under the owner's delegation of 2026-10-02. Date: 2026-10-03.
Milestone: E14. A correction to ADR-0162, which recorded §15.6 test 11,
"`MenuChanged(store_47)` invalidates store 47 only", as met.

## Context

- **ADR-0162 met test 11 for pages.** A change to store 47's menu patches the
  documents showing store 47 and no other, and each store has a menu
  fragment of its own.
- **The server's query cache was dropped by the query's name.** On any
  change to store 47's menu, the development server ran
  `self.queries.invalidate("store.page.Menu")`. That dropped every store's
  kept menu. Store 48's next document read its menu from the data layer
  again, though nothing about it had changed. A server test fails before
  this change: three reads of the menus, where two are right.
- **The program did not say it.** The store's `Menu` query declared no
  `invalidates_on`. The server named the query in its own code. `Events.pw`
  states the rule the drop broke: "An event's parameters are its identity,
  and they are what makes `MenuChanged(store_47)` narrower than
  `MenuChanged`." The menu fragment declares `invalidates_on
  MenuChanged(id)`; the query it reads did not.
- **The mechanism existed.** A command's emitted events reach the queries
  that declare them through the graph (ADR-0127). The server binds the
  event's arguments to each query's parameters by the names its
  `invalidates_on` gives them, and drops that one entry.

## Decision

1. **The store's `Menu` declares `invalidates_on MenuChanged(id)`.**
2. **The development server's menu change is the event `MenuChanged(47)`.**
   It drops what the graph says depends on that event, by the path a
   command's events take, and only store 47's entries.
3. **A host applies what the program declares.** A program whose menu query
   declares no `invalidates_on` keeps its menu for its `freshness`. The
   benchmark's store is such a program; none of its tasks changes the menu.

## Alternatives

- **Keep the drop in the server's code, scoped to the key**
  (`invalidate_key(Menu, 47)`). It is right for this store. But the server
  would still name the program's query, so a query named otherwise, or a
  second query that depends on the menu (the store's recommendations,
  next), would be served stale. The declaration is what the materializer
  already reads.
- **Commit the menu change through the materializer's outbox**, as a
  command's events are. The fragment and the page's patch are produced in
  the change's own order (E7-P), which a drain would reorder. Nothing in
  the query cache needs it.

## Acceptance

- The server's test `a_menu_change_drops_that_stores_kept_menu_only`:
  - control: each store's menu is kept, so serving both again reads
    neither;
  - after store 47's menu changes, store 48's is still kept;
  - store 47's is read again, and shows the change.

  It failed before the change.
- `a_menu_change_drops_the_menus_kept_values` (ADR-0127) still holds, on the
  graph regenerated by `just materialize`.
- The browser suite.
- `scripts/menu_changed_mutations.py`: 5 mutants, recorded by
  `just e14-menu-changed`.

## Not claimed

- **The fragment's invalidation is still named in the server's code**, as
  `menu_key(47)`. It is per store, so it is right; the materializer's drain
  reaches only the cart's entries today.
- **`InventoryChanged`.** `MenuItem` has no `available` field yet (the
  audit's first gap, what remains of it), so an item's stock changes nothing
  the menu shows.
